# 007: Cooking stations in the graybox

## Goal
The first playable cooking loop on the dedicated server: players carry ingredients to a board,
pan, pot and counter, cut, fry, boil, mix and plate them, and see the result's name. Every
operation runs on the server through spec 005 `ItemFactory`; clients only send intents and only
receive names and coarse display hints, never stats, quality or exact values (D2, D21).

## Design

### Who decides what
| Data | Where it lives | Client sees |
|---|---|---|
| `Item` (stats, components, tree, hash) | Server, `ItemInstanceRegistry` | nothing |
| Rating / quality | Server, computed on demand by `ItemRater` | nothing (Open question 4) |
| Display name | Server computes with `ItemNaming.Resolve` | `FoodItem.DisplayName` SyncVar |
| Base id of first component, browning step 0..3 | Server | SyncVars, for colour only |
| Station slots, heat setting, heat start tick | Server | slot occupancy, temp **bucket label**, elapsed time **bucket label** |
| Exact temperature, exact elapsed seconds | Server | never (D21) |

### Food items on the network
- Every `Item` in the world is one spawned `FoodItem` NetworkObject (prefab: 0.2 m cube with
  `Pickup`, `FoodItem`, server-authoritative NetworkTransform). It is carried with the spec 003
  pickup flow, so pickup reach (2.5 m), one item per player and race rules apply unchanged.
- `ItemInstanceRegistry` (server, plain C#): `long Register(Item item)` allocates instance ids
  1, 2, 3, ... (never reused within a server run; these become spec 008's `instanceId`),
  `bool TryGet(long id, out Item item)`, `bool Remove(long id)`, `int Count`. Capacity
  `MaxFoodItems = 200`; `Register` on a full registry returns 0 and callers report `WorldFull`.
- `FoodItem` SyncVars (server writes): `InstanceId` (long, needed later for selling),
  `DisplayName` (string, at most 96 chars, longer names are cut with "..."), `VisualBaseId`
  (string, first component's base id), `BrowningStep` (byte 0..3 from `Doneness` in quarters,
  a colour hint only). Nothing else of the item is replicated.
- `FoodItemService` (server): `Spawn(Item item, Vector3 at) -> FoodItem?` registers and spawns;
  `Consume(FoodItem f)` removes from the registry and despawns. Inputs of an operation are
  consumed in the same server step as the output is spawned.

### Stations
`StationKind` = `Board`, `Pan`, `Pot`, `Counter`, `Bin`. The kind maps to the spec 005
`OperationDef.Station` label: Board = `board`, Pan = `pan`, Pot = `pot`, Counter = `counter`.
`StationRules.Allows(kind, OperationDef)` is true only on a match, so fry on the board fails.

| Station | Slots | Actions | Op |
|---|---|---|---|
| Board | 1 | `Cut(shape)` | cut, instant |
| Pan | 1 | `SetTemp(+/-)`, heat starts on place, ends on take | fry (default) or saute (`ToggleMode`) |
| Pot | 1 | heat starts on place, ends on take | boil, fixed 100 C |
| Counter | 6 | `Mix`, `Plate` | mix (2..6 items), plate (1..4 items) |
| Bin | 0 | place = discard | none (item consumed, `Discarded` event) |

- `StationSlots` (plain C#): fixed capacity, `TryPlace(long instanceId)`, `TryTakeLast(out long)`,
  `IReadOnlyList<long> Items` in placement order. Mix and plate pass the items in placement order;
  spec 005 sorts commutative inputs itself, so order does not matter for the result.
- Reach: the player must be within `StationRules.MaxReach = 2.5 m` of the station's interaction
  point for every station intent (same constant as spec 003 pickups).

### Heat: time is real, buckets are what players see
- `CookingTime`: `TimeScale = 6` sim seconds per real second (Open question 2), so fries at
  150 sim s take 25 real s and a long boil (900 sim s) takes 150 real s.
- `HeatSession` (plain C#) stores `StartTick`, `TempC` (int) and the op id. On take:
  `simSeconds = (endTick - startTick) * TimeScale / tickRate` (double, from FishNet's tick rate),
  clamped to the op's `time` Max. Below the op's `time` Min the item is returned unchanged and
  the outcome is `TooShort` (no new item, no hash change). Otherwise `ItemFactory.Apply(opId,
  [input], { temp = TempC, time = simSeconds })` (boil has no temp param).
- Temperature: pan knob in 10 C steps, range from the fry/saute `temp` param (120..220);
  a new pan starts at `CookingTime.PanStartTempC = 170` (spec 005 params have no default). The temp can only be changed while the pan is empty (Open question 3).
  Clients send `+1`/`-1` steps, never a value. The pan shows the temp bucket label ("hot") and,
  while cooking, the bucket label of the elapsed time ("lightly", "", "dark"), updated by the
  server when the bucket changes, not every tick.
- Ticks, not `Time.time`: elapsed time comes from FishNet's tick counter so it is the same on
  host and dedicated server and independent of frame rate.

### Intents (ServerRpcs on `StationInteractor`, all on the player object, `RequireOwnership = true`)
```csharp
enum StationAction : byte { Place, Take, Cut, SetTempUp, SetTempDown, ToggleMode, Mix, Plate }
[ServerRpc] void RequestStation(NetworkObject station, StationAction action, byte choice);
```
`choice` is only used by `Cut`: index into the cut op's `shape` buckets (0 halves, 1 slices,
2 sticks, 3 cubes). The server checks in this order and replies with a `TargetRpc` carrying a
`CookingOutcome`: station exists and is a `Station` (`NotFound`), reach (`TooFar`), action valid
for this kind (`WrongStation`), slot state (`StationFull`, `StationEmpty`, `NotHolding`,
`HandsFull`), `choice` in range (`InvalidChoice`), then `ItemFactory.Apply`
(`OperationError` mapped to `CookingOutcome.OperationFailed` plus the error code), world cap
(`WorldFull`), else `Ok`. Invalid intents never throw and never change state.
No RPC in `Worktown.Game.Cooking` takes a hash, stat, quality, float, item id or name from the
client (AC8).

### Flows
- **Place**: player holds a food item, `E` on a station. `PickupService.ServerTakeHeld(player)`
  releases the registry claim and returns the item; the station attaches it to its slot
  transform. Pan/Pot: a `HeatSession` starts with the current tick.
- **Take**: hands empty, `E` on a station. Pan/Pot: the session ends and the heat op is applied;
  the output item (or the unchanged input on `TooShort`) goes into the player's hand via
  `PickupService.ServerGive(player, item)`. Other stations: the last placed item is given back.
- **Cut / Mix / Plate**: `F` cut with the selected shape (`1`..`4` select), `F` mix, `G` plate on
  the counter. The inputs are consumed and the output is placed in the first slot. Spec 005's
  cut no-op returns the input item itself: then nothing is consumed or spawned.
- **Disconnect**: spec 003 drops the held item. Items on stations stay; a running heat session
  keeps running and anyone can take the item off.
- **Co-op**: any player can take any item from any station; no ownership of food in this spec.

### Dev ingredient crates (temporary, Open question 1)
Spec 008 says base items enter the world only after an Ok `TryBuyBase`. There is no in-game
economy yet, so this spec adds `IngredientCrate` stations, one per `StarterItems` base id, that
spawn one base item into the player's hand on `E` (`ItemFactory.CreateBase`). They exist only when
the server runs with `-devcrates` or in the Editor; otherwise the builder places none and the
server refuses crate intents with `NotFound`. The economy-in-game spec replaces them with the grocer.

### Hooks for later specs (server-side C# events on `CookingService`)
`OperationApplied(int clientId, string opId, IReadOnlyList<Item> inputs, OperationResult result)`
after every Ok `Apply` that produced a new item (for spec 008 `Byproducts.ForOperation`), and
`Discarded(int clientId, long instanceId, Item item)` at the bin (for `EconomyEngine.Discard`).
No subscriber in this spec except a server log line.

### Logging (server, one line per Ok operation)
`[Cook] client 3 fry(temp=hot,time=medium;cut(shape=sticks;potato)) q=696 -> "crispy fried potato sticks" #12`.
Quality appears only in server logs (dev feedback for tuning). Hashes are not logged in full
(first 12 chars) to keep logs short.

### StarterItems (in /sim, provisional values = the spec 005 `TestItems` fixtures)
Ids: `apple`, `basil`, `cheese`, `oil`, `onion`, `potato`, `salt`, `tomato`, the same set as
spec 008's grocer table, with stats, ideal doneness windows and tags copied unchanged from
`sim/Sim.Tests~/Cooking/TestItems.cs`. `TestItems` stays as it is (tests must not depend on
data that will be retuned). Display names are the ids in plain English ("potato").

### Scene
`GrayboxSceneBuilder` adds a kitchen corner near the spawn: one Board, two Pans, one Pot, one
Counter, one Bin, and 8 crates in a row (crates only with dev crates enabled, see above). Each
station has a world-space text label with its kind for the graybox. Stations are static scene
NetworkObjects.

## Open questions (answered 2026-11-07: human approved all recommended defaults)
1. **Ingredient source until the economy is in the game.** Default: dev crates behind
   `-devcrates`, replaced by the grocer later. Alternative: pull accounts, a starting grant and
   `TryBuyBase` into this spec (bigger, and needs the starting-grant decision from spec 008 Q12).
2. **Cooking time scale.** Default: 6 sim seconds per real second (fries ~25 s, long boil
   ~2.5 min). Alternative: 1:1 (fries 2.5 min) or a different factor.
3. **Changing the pan temperature while cooking.** Default: not allowed, set it before placing.
   Alternative: allowed, using the time-weighted mean temperature for the heat op.
4. **Quality feedback to players.** Default: none in this spec (server log only), decide with the
   economy-in-game spec when selling makes quality visible. Alternative: a coarse 1 to 5 star
   SyncVar on `FoodItem` now.
5. **Starter item data.** Default: a provisional `StarterItems` in /sim with the `TestItems`
   values, so game, economy and tests share one id set until the ~15 item data file exists.
   Alternative: hard-code the catalog in /game.
6. **Controls.** Default: `E` place/take (existing pickup key), `F` cut/mix, `G` plate, `1`..`4`
   shape, `R`/`T` temp down/up, `M` pan mode fry/saute. Provisional until the input/UI spec.
